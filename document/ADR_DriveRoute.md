## ADR-001 — ルーティングエンジンに Google Routes API v2 を採用する

**ステータス**: 採用済み  
**決定日**: 2025年（Week 0）  
**決定者**: エンジニアリードチーム

### コンテキスト

ルート間の距離・所要時間・交通情報をリアルタイムに取得するAPIが必要。候補として以下を検討した。

### 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| **Google Routes API v2** | 精度・カバレッジが最高水準。日本国内の交通情報に強い。既存の Places API との統合が容易 | コストが高い（$5〜10/1000req）。ベンダーロックイン |
| OpenRouteService (OSM) | 無料〜低コスト。オープンソース | 日本国内の精度が低い。リアルタイムトラフィック未対応 |
| HERE Routing API | 商用レベルの精度 | コストが Google 同等。認知度低くサポート不安 |
| Mapbox Directions API | SDK が充実 | 日本の高速道路料金との連携なし |

### 決定理由

- 日本国内の道路精度と交通情報リアルタイム性が最重要要件
- 既に Places API を採用しており、同一ベンダーで SDK・認証を統一できる
- $200/月の無料枠で MVP 段階のコストはほぼゼロに抑えられる見込み

### 覆す条件

- 月額コストが $500 を恒常的に超えた場合
- Google が API を廃止または大幅値上げした場合
- OSM の日本精度が大幅改善された場合

## ADR-002 — LLM に Gemini Pro 1.5 を採用する（GPT-4o ではなく）

**ステータス**: 採用済み  
**決定日**: 2025年（Week 0）  
**決定者**: エンジニアリードチーム

### コンテキスト

ルート説明文（200字）の自動生成に LLM が必要。非同期・低レイテンシ・低コストが優先条件。

### 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| **Gemini Pro 1.5** | Google エコシステム統合（認証・課金を一元化）。コスト低。日本語品質が GPT-4 と同等以上 | GPT-4 ほどの実績がない |
| GPT-4o (OpenAI) | 日本語品質・指示追従性が非常に高い | コストが高い（Gemini の約3倍）。別ベンダー管理が必要 |
| Claude 3 Haiku | 最速・最安 | 長文コンテキストの品質が他より低い |
| Llama 3 (自前ホスト) | コスト最小 | 運用負荷大。日本語品質が商用モデルに劣る |

### 決定理由

- Google Cloud の統一課金・認証で運用コストを削減
- 説明文生成は非クリティカルパス（非同期）のため、GPT-4o の優位性が活きない
- 月間コストを Gemini で抑え、その分 Google Maps API 枠に充てる

### 覆す条件

- Gemini の日本語品質がユーザー調査で著しく低評価となった場合
- OpenAI が Google Maps 相当の地図統合 SDK を提供した場合

## ADR-003 — バックエンドに Supabase（Postgres）+ Vercel Serverless を採用する

**ステータス**: 採用済み  
**決定日**: 2025年（Week 0）

### コンテキスト

チーム規模 2〜3名、8週間 MVP。インフラ運用コストをゼロに近づけながら、認証・DB・API を提供する必要がある。

### 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| **Supabase + Vercel** | 認証・DB・Edge Functions・RLS を一元管理。小チームの生産性が最高 | スケール時の柔軟性がやや低い |
| AWS (RDS + Lambda) | スケーラビリティ最高。本番実績豊富 | 初期設定・運用コストが大きい。MVP に過剰 |
| Firebase + GCP | Google エコシステム統合 | Firestore は SQL が使えない。集計クエリが苦手 |
| PlanetScale + Railway | 分散 DB で大規模に強い | チームの学習コストが高い |

### 決定理由

- Supabase RLS（Row Level Security）で users テーブルの行レベル認可を宣言的に実装できる
- Vercel の Next.js ネイティブ統合により CI/CD をゼロ設定で実現
- 無料枠（Supabase 500MB DB + Vercel hobby）で MVP を完全に賄える

### 覆す条件

- 月間アクティブユーザーが 10,000 を超え、Supabase Pro では接続数が不足した場合
- 地理空間クエリ（PostGIS）で Supabase の制限に当たった場合

## ADR-004 — 高速料金を NEXCO 料金表キャッシュで計算する（公式 API なし）

**ステータス**: 採用済み（リスク承認済み）  
**決定日**: 2025年（Week 0）

### コンテキスト

NEXCO（高速道路会社）はリアルタイム料金取得 API を一般公開していない。高速料金の精度はサービスの核心だが、データソースに限界がある。

### 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| **NEXCO 料金表を DB にキャッシュ** | 実装可能・コスト低 | 更新が手動。ETC2.0 等の複雑な割引が完全再現困難 |
| 外部有料 API（ドラぷら等） | 精度高 | API 提供状況が不明瞭。コスト未確定 |
| Google Maps「通行料金」フィールド | 実装容易 | 精度が低く区間料金の内訳が取れない |
| スクレイピング | 無料 | 規約違反リスク大。ADR-001 で原則禁止と決定 |

### 決定理由

- NEXCO 料金表は PDF・HTML で公開されており、手動 ETL で DB 整備が可能
- ユーザーへの「概算」表示と免責事項で精度リスクを明示する
- 有料 API が整備されれば移行する（疎結合設計にしておく）

### 覆す条件

- NEXCO が公式 API を公開した場合（最優先で移行）
- 料金誤差によるユーザークレームが頻発した場合

## ADR-005 — フロントエンドに Next.js App Router を採用する（Pages Router ではなく）

**ステータス**: 採用済み  
**決定日**: 2025年（Week 0）

### コンテキスト

Next.js のアーキテクチャ選択。App Router（React Server Components）か Pages Router（従来型）か。

### 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| **App Router（RSC）** | Server Components で Google Maps API キーをサーバー側に閉じ込められる。データフェッチが宣言的 | エコシステムが新しく、ライブラリ対応にばらつき |
| Pages Router | 枯れた技術。ライブラリ対応が完全 | `getServerSideProps` の記述量が多い。APIキー保護が煩雑 |

### 決定理由

- Google Maps API キー・Supabase 接続文字列をクライアントに露出させないために Server Components が有効
- Vercel の App Router 最適化（Streaming・PPR）が利用可能
- チームメンバーが React 18 + RSC の経験あり

### 覆す条件

- 使用ライブラリ（地図 SDK 等）が App Router と非互換であることが判明した場合
