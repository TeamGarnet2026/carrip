## 1. パフォーマンス要件

### 1-1. レスポンスタイム（SLO）

| 操作 | 目標値（p95） | 上限値（p99） | 計測ポイント |
|---|---|---|---|
| ルート候補3案の生成 | 20秒以内 | 30秒以内 | POST /api/routes/generate |
| POI 変更後の費用再計算 | 2秒以内 | 3秒以内 | PATCH /api/routes/:id/stops |
| 共有 URL 生成 | 1秒以内 | 2秒以内 | POST /api/routes/:id/share |
| 静的ページ（LCP） | 2秒以内 | 3秒以内 | Lighthouse 計測 |
| API 全般（上記以外） | 500ms以内 | 1秒以内 | Vercel Analytics |

> 注意：ルート生成はLLM非同期呼び出しを含むため目標値が長め。UX上はプログレスバーで体感待機時間を軽減する。

### 1-2. スループット

| 条件 | 目標値 |
|---|---|
| 同時接続ユーザー数（MVP） | 50セッション |
| ルート生成リクエスト（MVP） | 10req/分/IP（レート制限値） |
| DBコネクション数 | 最大20（Supabase Free上限） |

### 1-3. Lighthouse スコア目標

| 指標 | 目標値 |
|---|---|
| Performance | 80以上 |
| Accessibility | 90以上 |
| Best Practices | 90以上 |
| SEO | 80以上 |

## 2. 可用性・信頼性要件

### 2-1. 稼働目標（SLO）

| 指標 | MVP目標 | Phase 2目標 |
|---|---|---|
| 月間稼働率 | 99.0%（7.2時間/月ダウン許容） | 99.5%（3.6時間/月） |
| 計画メンテナンス | 深夜2〜4時、週1回以内 | 深夜2〜3時、月1回以内 |
| RTO（目標復旧時間） | 4時間以内 | 2時間以内 |
| RPO（目標復旧時点） | 24時間以内 | 1時間以内 |

> Vercel + Supabase のマネージドサービスが基盤のため、インフラ稼働率は依存サービスの SLA に準ずる。  
> （Vercel SLA: 99.99%、Supabase SLA: 99.9%）

### 2-2. 外部API障害時のフォールバック

| 外部サービス | 障害時の挙動 |
|---|---|
| Google Places API | Redisキャッシュから最大7日前のPOI情報を返す。キャッシュなければエラー表示 |
| Google Routes API | キャッシュされた距離データで概算計算。「精度が低下しています」バナーを表示 |
| Gemini API | LLM説明文の生成をスキップ。カードにコメント欄を空白で表示 |
| gogo.gs（ガソリン価格） | 資源エネルギー庁の月次データ（S3保存）をフォールバックとして使用 |

## 3. セキュリティ要件

### 3-1. 認証・認可

| 要件 | 仕様 |
|---|---|
| 認証方式 | Supabase Auth（メール+パスワード、Google OAuth） |
| セッション管理 | JWTトークン、有効期限1時間、リフレッシュトークン7日 |
| 行レベル認可 | Supabase RLS にて `trips.owner_id = auth.uid()` を必須条件とする |
| 共有URLのアクセス | 認証不要（short_code による参照のみ）。編集・削除は不可 |
| APIキー管理 | 全APIキーをVercel環境変数に格納。クライアントバンドルに含めない |

### 3-2. 入力サニタイズ・バリデーション

| 対象 | 対策 |
|---|---|
| 住所テキスト入力 | Google Places Autocomplete で有効住所のみ受け付ける |
| 数値パラメータ（人数・日数） | サーバー側で型・範囲チェック（Zod スキーマ） |
| SQLインジェクション | Supabase クライアント SDK のパラメータバインディングを常に使用。生クエリ禁止 |
| XSS | Next.js のデフォルト HTML エスケープ + DOMPurify を LLM 出力に適用 |

### 3-3. データ保護

| 要件 | 仕様 |
|---|---|
| 通信暗号化 | 全通信 HTTPS（TLS 1.2以上）。Vercel がデフォルト適用 |
| 保存データ暗号化 | Supabase（PostgreSQL）の保存時暗号化を有効化 |
| 個人情報最小化 | 保存するのは出発地・旅程データのみ。氏名・電話番号は収集しない |
| 共有URLの失効 | `expires_at` = 作成日 + 7日。失効後は 404 を返す |
| ログの個人情報 | アクセスログに住所・旅程データを含めない（IPのみ） |

### 3-4. OWASP Top 10 対応状況

| 脅威 | 対策 |
|---|---|
| A01 アクセス制御の不備 | Supabase RLS + JWT 検証 |
| A02 暗号化の失敗 | TLS + DB暗号化 |
| A03 インジェクション | パラメータバインディング・Zod バリデーション |
| A07 認証の失敗 | Supabase Auth（ブルートフォース対策内蔵） |
| A09 セキュリティログの失敗 | Sentry によるエラー監視・アラート |

## 5. 運用・保守要件

### 5-1. 監視・アラート

| 項目 | ツール | 閾値・条件 |
|---|---|---|
| エラー監視 | Sentry | エラー率 1%超で Slack 通知 |
| パフォーマンス | Vercel Analytics | p95 > 30秒 で通知 |
| API コスト | Google Cloud Billing | $150/月超で通知 |
| DB 使用量 | Supabase ダッシュボード | 400MB超で確認 |
| ユーザー行動 | PostHog | ファネル離脱率の週次レポート |

### 5-2. データ保持期間

| データ種別 | 保持期間 | 削除方針 |
|---|---|---|
| trips（旅行プラン） | 1年間（最終アクセスから） | バッチで定期削除 |
| shares（共有URL） | expires_at + 30日 | 失効後30日でバッチ削除 |
| approvals（承認履歴） | 対応する share と同期 | share 削除時に CASCADE |
| external_prices（価格キャッシュ） | 90日 | TTL で自動削除 |
| アクセスログ | 90日 | Vercel 側で自動削除 |

### 5-3. バックアップ

| 対象 | 頻度 | 保持期間 | 方法 |
|---|---|---|---|
| Postgres DB | 日次 | 7日 | Supabase 自動バックアップ |
| NEXCO 料金 DB | 週次 | 4週 | S3 バケットに手動 |
| ガソリン価格データ | 月次 | 3ヶ月 | S3 バケットに手動 |
