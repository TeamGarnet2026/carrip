## 4. 機能要件

機能要件定義書 DriveRoute Optimizer v1.0

### 4-1. 目的と適用範囲

本文書はDriveRoute OptimizerのMVP（Phase 1）における機能要件を定義する。開発チームが実装すべき機能の範囲・ふるまい・受け入れ条件を明確化し、PO・デザイン・QAと共通認識を確立することを目的とする。

| 区分 | 内容 | 備考 |
|------|------|------|
| 対象システム | DriveRoute Optimizer Webアプリ（Next.js） | フロントエンド + APIサーバー |
| 対象フェーズ | Phase 1（MVP） | Phase 2以降の要件は別文書 |
| 対象ユーザー | グループドライブ旅行の幹事・参加者 | 4ペルソナ定義あり |
| 対象外 | ネイティブアプリ・非機能要件・インフラ構成 | 別文書参照 |

### 4-4. ユーザーストーリーと受け入れ条件

**US-01：ルート候補の自動生成**

旅行者として、出発地・訪問県・人数・車種・日数を入力するだけで、費用内訳付きの候補ルートを3案受け取りたい。

受け入れ条件：
- 入力完了から15秒以内に候補ルート3案が表示される（タイムアウト時はエラーコード DR-RTE-003 を返す）
- 各案に総距離（km）・総時間（分）・総費用（円）・1人あたり費用（円）が表示される
- 費用内訳として燃料費・高速料金・駐車料金・入場料が個別に表示される
- POIの営業時間・定休日が考慮され、旅行日に訪問不可のPOIは候補から除外される
- 候補ルートはスコア降順で表示される
- 入力エラー時は該当フィールドに即時バリデーションメッセージが表示される

**US-02：費用のリアルタイム再計算**

旅行者として、ルートのPOIを追加・削除・並び替えしたとき、費用が即座に更新されてほしい。

受け入れ条件：
- POI変更後15秒以内に費用が再計算されて画面が更新される
- 変更前後の費用差分が +/- で色付きハイライト表示される（増加：赤、減少：緑）
- 設定した予算を超過した場合、画面上部に警告バナーが表示される
- POIのドラッグ&ドロップによる並び替えが可能で、移動後に自動再計算される
- 再計算中はローディングインジケーターが表示される

**US-03：グループ共有・閲覧**

幹事として、確定したルートをLINEグループに送り、メンバーの共有をしたい。

受け入れ条件：
- 「LINEで共有」ボタンから1タップでLINEアプリが起動し、共有相手を選択し共有
- 共有URLを開いたメンバーはアカウント登録不要でルートを閲覧できる
- 共有URLは予定日から30日後に自動失効し、失効後はエラーページが表示される

### 4-6. 機能要件詳細

**FR-01：ルート候補自動生成機能**

| 属性 | 内容 |
|------|------|
| 要件ID | FR-01 |
| 機能名 | ルート候補自動生成 |
| 優先度 | Must（MVP必須） |
| 関連US | US-01 |
| エンドポイント | POST /api/routes/generate |
| レスポンスタイム | 15秒以内（p95）。タイムアウト時はDR-RTE-003を返す |
| 事前条件 | 必須入力パラメータが全て有効値であること |
| 事後条件 | 候補ルート3案がJSON形式で返却される |

処理フロー：
- 入力バリデーション（Zodスキーマ）— エラー時は 400 を返す
- POI候補選定：Google Places APIで最大50件取得 → 多段フィルタリングで最大15件に絞り込む
- TSP近似：貪欲法で初期ルート生成 → 2-opt改善（POI数 ≤ 8 の場合のみ）
- 日程分割：旅行日数 ≥ 2 の場合、1日の走行を12時間以内に収まるよう日ごとにPOIを振り分ける
- 休憩挿入：連続走行上限（デフォルト120分）を超えるセグメントにSA・道の駅を自動挿入する
- 費用計算：燃料費・高速料金・駐車料金・入場料を算出し合計・1人あたり換算する
- スコアリング：総合スコア計算式で評価し上位3案を選定する
- レスポンス返却：3案 + 費用内訳

**FR-02：費用計算機能**

| 属性 | 内容 |
|------|------|
| 要件ID | FR-02 |
| 機能名 | 費用計算（燃料費・高速料金・駐車料金・入場料） |
| 優先度 | Must |
| 関連US | US-01, US-02 |

| 費用項目 | 計算方式 | データソース |
|---------|---------|------------|
| 燃料費 | 走行距離 ÷ 実効燃費 × ガソリン単価　実効燃費 = カタログ燃費 × 車種係数 × 道路係数 × 季節係数 | 政府API（平均価格） |
| 高速料金 | 通過ICリスト × NEXCO料金表 + ETC割引（休日30% / 深夜30% / 朝夕最大50%） | NAVITIME API 2.0 |
| 駐車料金 | Σ（各POIの駐車料金 × 滞在時間） | NAVITIME API 2.0 |
| 入場料 | Σ（各POIの入場料 × 人数） | Google Places API / 施設公式データ |

**FR-03：POIリアルタイム編集・再計算機能**

| 属性 | 内容 |
|------|------|
| 要件ID | FR-03 |
| 機能名 | POIリアルタイム編集・再計算 |
| 優先度 | Must |
| 関連US | US-02 |
| エンドポイント | PATCH /api/routes/:id/stops |
| レスポンスタイム | 3秒以内（p95） |

対応操作：
- 追加：POI検索（/api/pois/search）結果から1件選択して末尾または指定位置に追加する
- 削除：POIカード上の「✕」ボタンで該当POIを除外する
- 並び替え：ドラッグ&ドロップで順序変更し、移動後に自動再計算する
- 再計算：距離・時間・費用全項目を再計算し、変更差分をハイライト表示する
- 予算警告：費用が予算設定値を超過した場合、画面上部に警告バナーを表示する

### 4-7. スコアリング・アルゴリズム要件

**POI候補選定フロー**

| Step | 処理 | パラメータ・条件 | 出力 |
|------|------|----------------|------|
| 1 | エリア絞り込み | 訪問都道府県内 | 候補エリア確定 |
| 2 | カテゴリー検索 | 優先軸に応じたPlacesタイプ・上位50件取得 | 粗候補リスト |
| 3 | 品質フィルター | 評価 ≥ 3.8・口コミ ≥ 20 | 絞り込み済みリスト（上位30件） |
| 4 | 運用フィルター | 旅行日時との営業時間・定休日照合 | 訪問可能リスト（上位20件） |
| 5 | 密度調整 | 500m以内の近接POIを間引き（haversine距離） | 最終候補リスト（最大15件） |

**ルート生成アルゴリズム**

| 処理 | アルゴリズム概要 | 計算量 | 適用条件 |
|------|---------------|--------|---------|
| 初期解生成（貪欲法） | 出発地から最も近いPOIを順次選択してルートを構築 | O(n²) | 常に適用 |
| 2-opt改善 | 2辺を入れ替えてルート総距離が短縮されれば採用を繰り返す | O(n² × iter) | POI数 ≤ 8 のみ |
| 日程分割 | 日数≥2の場合、POIを日ごとに振り分け（1日走行≤12時間） | O(n) | 旅行日数 ≥ 2 |
| 休憩挿入 | 連続走行上限超のセグメントにSA・道の駅を自動挿入 | O(m) | 常に適用 |

**ルートスコアリング**

スコア計算式：score = w_cost×cost_score + w_time×time_score + w_poi×poi_score + w_scenic×scenic_score

| スコア項目 | 重み(w) | ユーザー調整 | 補足・ペナルティ |
|-----------|--------|------------|----------------|
| コストスコア (w_cost) | 0.35 | 優先軸「コスト重視」で0.50に上昇 | 予算超過ルートはペナルティ × 0.5 |
| 時間スコア (w_time) | 0.25 | 「時間効率」優先で0.40に上昇 | 1日8時間超はペナルティ適用 |
| POI評価スコア (w_poi) | 0.25 | 固定 | Google評価 × レビュー数で正規化 |
| 優先軸一致スコア (w_scenic) | 0.15 | 「景観・温泉」等の選択で0.30に上昇 | カテゴリタグのマッチ率 |

### 5-3. セキュリティ要件

**認証・認可**

| 要件 | 仕様 |
|------|------|
| 認証方式 | Supabase Auth（メール+パスワード、Google OAuth） |
| セッション管理 | JWTトークン、有効期限1時間、リフレッシュトークン7日 |
| 行レベル認可 | Supabase RLS にて trips.owner_id = auth.uid() を必須条件とする |
| 共有URLのアクセス | 認証不要（short_code による参照のみ）。編集・削除は不可 |
| APIキー管理 | 全APIキーをVercel環境変数に格納。クライアントバンドルに含めない |

**入力サニタイズ・バリデーション**

| 対象 | 対策 |
|------|------|
| 住所テキスト入力 | Google Places Autocomplete で有効住所のみ受け付ける |
| 数値パラメータ（人数・日数） | サーバー側で型・範囲チェック（Zodスキーマ） |
| SQLインジェクション | Supabase クライアントSDKのパラメータバインディングを使用。生クエリ禁止 |
| XSS | Next.jsのデフォルトHTMLエスケープ + DOMPurify をLLM出力に適用 |

**データ保護**

| 要件 | 仕様 |
|------|------|
| 通信暗号化 | 全通信 HTTPS（TLS 1.2以上）。Vercel がデフォルト適用 |
| 保存データ暗号化 | Supabase（PostgreSQL）の保存時暗号化を有効化 |
| 個人情報最小化 | 保存するのは出発地・旅程データのみ。氏名・電話番号は収集しない |
| 共有URLの失効 | expires_at = 作成日 + 7日。失効後は 404 を返す |
| ログの個人情報 | アクセスログに住所・旅程データを含めない（IPのみ） |

**OWASP Top 10 対応状況**

| 脅威 | 対策 |
|------|------|
| A01 アクセス制御の不備 | Supabase RLS + JWT 検証 |
| A02 暗号化の失敗 | TLS + DB暗号化 |
| A03 インジェクション | パラメータバインディング・Zod バリデーション |
| A07 認証の失敗 | Supabase Auth（ブルートフォース対策内蔵） |
