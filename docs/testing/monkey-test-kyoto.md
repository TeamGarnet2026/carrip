# モンキーテスト（京都での実地テスト・地元レビュー）（#700）

実際の観光地（京都）でアプリを使い、地元の人からフィードバックをもらう。
要件定義書「11. テスト計画・品質基準」の「モンキーテスト、京都にて実施し地元の人に結果についてレビューをもらう」に対応する。

## 目的

- 決められた手順ではなく、利用者が思いつくままに操作して、想定していない不具合・使いにくさを見つける
- 京都をよく知る人に、提案されたルート・立ち寄り先・費用・所要時間が現実的かを見てもらう

## 前提

- 全機能の実装・テストが完了し、本番環境にデプロイされている
- 本番環境の URL・テスト用アカウントを用意している（テスト用アカウントはこの文書に書かない）
- 当日の Google Places / NAVITIME の利用回数に余裕がある
  - Places API は1日 150 回まで。上限に達すると行き先画面に「無料プランは終了しました」と出る
- 障害が起きたときの連絡先・手順（`docs/incident.md`）をメンバー全員が確認している

## 進め方

1. 協力者に、アプリの目的（グループドライブの計画と費用の割り勘）だけを伝える。**操作方法は説明しない**
2. 協力者に自由に使ってもらい、メンバーは横で観察して「迷った・止まった・間違えた」場面を記録する（下の「観察記録」）
3. 次の課題を、協力者が思いつく条件でやってもらう
   - 課題1：京都駅から出発して、行きたい場所を3か所回る日帰りのプランを作る
   - 課題2：行き先を1つ入れ替えて、費用がどう変わるかを見る
   - 課題3：プランを保存し、LINE または QR コードで他の人に送る
4. 終わったら「フィードバック用紙」に沿って聞き取る
5. 次の操作も意図的に試す（モンキーテスト）
   - 戻る・進むボタンの連打、画面の再読み込み、途中でアプリを閉じて再度開く
   - 出発地に存在しない地名・記号・とても長い文字列を入れる
   - 電波の弱い場所・機内モードで操作する
   - 現在地の取得を拒否する
   - 画面を回転する、文字サイズを大きくする

## 改善点の整理

実施後、観察記録とフィードバックから改善点を整理する。改善の実装はスコープ外のため、**1件ずつ別のイシュー**にする。

| No | 改善点 | 根拠（観察記録 No / 協力者） | 種類 | 重要度 | 対応イシュー |
|---|---|---|---|---|---|
| 1 | | | 不具合 / 使いにくさ / 提案内容 / 要望 | 高 / 中 / 低 | # |
| 2 | | | | | |

重要度の目安：

- 高：プランを最後まで作れない、費用・ルートが明らかに誤っている
- 中：迷うが自力で解決できる、見積もりのずれが大きい
- 低：見た目・言葉づかい・あると便利な機能
